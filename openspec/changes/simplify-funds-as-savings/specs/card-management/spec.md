## 修改需求

### 需求:用户可自定义管理卡片
系统必须允许用户创建、重命名和删除储蓄卡，并为真实储蓄卡设置所需的初始金额；基金禁止再作为可管理卡片创建或展示，系统内置的虚拟消费账户也禁止出现在用户卡片管理中，禁止由用户创建、重命名或删除。

#### 场景:创建真实储蓄卡
- **当** 用户提交一张储蓄卡并填写名称与初始金额
- **那么** 系统必须持久化该卡片，并以初始金额作为余额计算的起点

#### 场景:禁止创建基金卡和消费卡
- **当** 用户打开设置或卡片管理页面
- **那么** 系统禁止提供“新建基金卡”或“新建消费卡”入口

#### 场景:重命名真实储蓄卡
- **当** 用户修改一张储蓄卡的名称为新的非空名称
- **那么** 系统必须更新该名称，且不影响该卡已有的余额与流水

#### 场景:删除真实储蓄卡
- **当** 用户删除一张储蓄卡
- **那么** 系统必须移除该卡片；若该卡仍存在关联数据或被设为默认卡，系统必须提示并阻止删除或要求先处理关联数据

#### 场景:基金池与虚拟消费账户不可按卡管理
- **当** 系统展示设置、卡片列表或消费工作区
- **那么** 系统禁止提供基金池或虚拟消费账户的卡片改名、删除、初始余额或排序操作

## 新增需求

### 需求:基金储蓄池只维护两个按月金额
系统必须提供唯一的基金储蓄池，并只允许用户按月份填写非负的当前市值与预充金额；系统禁止提供逐只基金、本金、盈亏、收益率或交易明细。

#### 场景:保存基金储蓄池
- **当** 用户选择月份并填写当前市值与预充金额后保存
- **那么** 系统必须以该月最后一次保存的两个数覆盖该月记录

#### 场景:查看历史月份
- **当** 用户查看某个没有精确记录的月份
- **那么** 系统必须展示不晚于该月的最近一条基金储蓄池记录，若此前从未填写则两项均为 0

#### 场景:旧基金迁移
- **当** 数据库中存在旧基金卡及本金、市值快照
- **那么** 系统必须把旧市值按月聚合为全局当前市值、将预充置 0，并移除旧本金和逐只基金数据
