## 上下文

消费侧最初使用 `cards(type=SPEND)` 与 `spendQuotas` 建模，后来额度来源迁移为“储蓄卡 → 消费卡”的 `consumptionBudgets`，但旧表、旧写入接口和用户可管理的多消费卡仍被保留。当前记账、详情、统计与对账分别组合这些数据，造成身份、月份和超支口径不统一；多储蓄卡页面还会分别使用同一份全局预充余额计算结转预览。

本变更涉及 IndexedDB 数据迁移、消费领域服务、记账与统计界面以及旧备份兼容。系统为纯前端本地 PWA，没有服务端可代替客户端执行迁移，因此升级与导入必须在本地原子完成并可重复执行。

## 目标 / 非目标

**目标：**

- 将消费侧收敛为系统唯一、不可由用户管理的虚拟消费账户，同时继续用统一账户承载全局消费流水。
- 当前月额度只由当前月所有储蓄卡消费预算求和得到；当前月超额充值同样按所有储蓄卡求和。
- 保留预充暂存和跨月结转，但严格区分“当月额度”和“历史暂存”。
- 让记账、详情、统计和对账共享同一组纯函数与统一 DTO，消除页面间口径差异。
- 安全迁移多张旧消费卡、旧额度记录与备份数据，不丢失流水、分类、日期、备注和金额。

**非目标：**

- 不要求消费流水选择实际付款的储蓄卡，也不从真实储蓄卡余额自动扣除某笔消费。
- 不取消超额充值、预充暂存、跨月结转或累计对账。
- 不改变储蓄卡、基金卡自身的预算和实际余额模型。
- 不引入账号、服务端同步或新的外部依赖。

## 决策

### 1. 使用系统管理的唯一虚拟账户，而不是用户可管理的消费卡

保留一个稳定的内部虚拟账户标识，使现有 `transactions.cardId` 索引与交易服务可以继续工作；该账户不出现在卡片管理、排序、默认卡和改名/删除界面中。记账路由直接打开消费工作区，用户无需也不能选择消费卡。

选择该方案而不是把消费交易拆到新表，是为了降低迁移范围并保留现有交易编辑、分类统计和备份结构。选择该方案而不是保留一张普通 `SPEND` 卡，是为了从产品层彻底消除“消费卡需要用户创建或选择”的误解。

### 2. `consumptionBudgets` 只保留“出资储蓄卡 + 月份”维度

新结构按 `[savingsCardId+month]` 唯一，移除 `consumptionCardId` 维度。月度额度定义为：

`B(m) = Σ consumptionBudget(savingsCardId, m)`

所有读取必须使用完整月份 `YYYY-MM` 精确匹配；按年统计可以逐月聚合，但按月视图禁止使用上一月、最近一条或累计额度代替本月额度。旧 `spendQuotas` 不再提供运行时读写接口，并在迁移完成后移除。

### 3. 超额充值按储蓄卡和月份直接求和

继续使用 `savingsEntries(kind=EXCESS)` 记录每张储蓄卡的超额充值，虚拟账户的月度超额充值定义为：

`X(m) = Σ excess(savingsCardId, m)`

不再按消费卡权重分配。该金额增加本月可用余额，但不改变本月额度，也不抹除“已消费超过预算”的事实。

### 4. 统一月度派生公式

对月份 `m`：

- `B(m)`：当前月额度。
- `X(m)`：当前月超额充值。
- `S(m)`：当前月全局消费流水合计。
- `R(m) = B(m) + X(m) - S(m)`：本月剩余。
- `O(m) = max(0, S(m) - B(m))`：消费超支。

页面只能展示共享领域服务返回的这些值，禁止在组件内重新组合另一套超支判断。超额充值可以使 `R(m)` 为正，但只要 `S(m) > B(m)`，仍必须展示 `O(m)`。

### 5. 预充暂存只影响结转与新转账，不影响额度

沿用按月正序递推的消费资金池：上月末暂存作为本月期初暂存，`C(m) = min(max(Pstart(m), 0), B(m))` 为本月使用的结转，`N(m) = B(m) - C(m)` 为本月需要的新转账。无论 `C(m)` 和 `Pstart(m)` 为多少，页面上的本月额度始终是 `B(m)`。

当多张储蓄卡共同填写预算时，结转只能在全局层计算一次。若界面需要展示每张储蓄卡的新转账贡献，则按各卡当月预算占比确定性分配 `C(m)`，最后一张卡吸收分币舍入差，确保各卡结转之和严格等于全局 `C(m)`；不得让每张卡独立使用完整期初暂存。

### 6. 数据迁移采用“新表优先、旧表兜底”

IndexedDB 升级时创建或确认唯一虚拟账户，将所有旧 `SPEND` 卡的消费流水重新关联到该账户，并按“储蓄卡 + 月份”汇总旧 `consumptionBudgets`。由于 v8 已经把 `spendQuotas` 复制过一次，为避免重复计入，只有当某月份不存在任何新预算记录时，才使用该月份的旧 `spendQuotas` 合计作为兜底，并归到默认或排序第一的储蓄卡。

迁移后删除多余消费卡和旧额度存储。旧备份导入先在内存中执行相同归一化，再以单个 Dexie 事务写入，避免导入后因数据库版本已升级而错过迁移。

### 7. 用专用消费工作区替代卡片详情

记账首页直接呈现唯一虚拟账户的日期、额度、已消费、剩余、超支与当日流水；消费详情不再显示卡名、“消费卡”标签、改名或删除操作。设置页移除“新建消费卡”。储蓄卡编辑页仍允许填写本卡当月消费预算和超额充值，但展示全局结转时必须明确区分“本卡贡献”和“全局合计”。

## 风险 / 权衡

- [旧数据可能同时存在于两套额度表，直接求和会翻倍] → 使用新表优先、旧表仅在整月无新数据时兜底，并为迁移编写重复数据测试。
- [多张旧消费卡合并后同日流水数量增加] → 保留每笔原始 ID、日期、分类、备注和金额，只改变账户归属，不合并交易记录。
- [固定内部账户仍是数据库中的一张卡，可能被通用卡片服务误显示] → 所有用户卡查询显式排除系统账户，并为设置、排序、默认卡和删除路径增加测试。
- [多卡结转按比例分配存在分币舍入] → 使用整数分计算并由确定的最后一张卡吸收尾差。
- [迁移失败会影响本地唯一账本] → 使用单事务、迁移前不删除旧数据、失败自动回滚，并保持备份导入可恢复。
- [年度统计聚合可能被误认为当前月额度] → DTO 明确区分月度与期间汇总，界面始终展示当前筛选范围标签。

## 迁移计划

1. 增加覆盖月度公式、多卡求和、跨月隔离与结转分配的纯函数测试。
2. 升级 IndexedDB schema，创建唯一虚拟账户并在单事务内归一化消费流水和预算数据。
3. 切换领域服务到单一预算源和统一月度 DTO，保留只读迁移兼容代码。
4. 更新记账、储蓄、设置和统计界面，移除用户可管理消费卡的入口与标签。
5. 更新备份导入/导出版本并用旧版样例验证迁移。
6. 验证成功后删除运行时旧额度 API；若升级失败，Dexie 事务回滚到旧 schema 与数据，用户仍可用旧版本导出备份。

## 待确认问题

无。唯一虚拟账户、多储蓄卡求和、超额充值、预充暂存、跨月结转和不关联实际付款卡的业务边界均已确认。
