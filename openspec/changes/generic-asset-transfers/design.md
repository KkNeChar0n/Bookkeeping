## 上下文

应用的储蓄余额是用户按月填写的真实余额快照，基金则在卡片上保存累计本金与当前市值。现有 `transactions` 调账只服务日常流水余额，不能解释月度储蓄快照到基金本金之间的迁移；旧版专用基金资金卡又把卡类型、批量注资和月度快照耦合在一起，已经回退。

本次在不恢复专用卡类型的前提下，引入独立的资产划转台账。正常划转既负责说明资金来源及去向，也会更新划转月份的储蓄余额：来源卡扣减，接收储蓄卡增加；转入基金时来源卡扣减且基金本金增加。历史补录仍只建立解释关系，避免重复改写已经包含该笔资金的余额和本金。

## 目标 / 非目标

**目标：**

- 用一个通用模型记录储蓄卡到储蓄卡、储蓄卡到基金本金的划转。
- 保证新增和撤销基金划转时，划转记录与基金本金原子一致。
- 保证新增和撤销正常划转时，来源与接收储蓄卡的当月余额原子一致。
- 支持“本金已包含”的历史补录，避免重复增加本金。
- 让统计可按截止月份累计基金投入，并从“利息/其他”残差中剥离。
- 所有基金本金人工校准均可审计，备份可完整往返。

**非目标：**

- 不恢复特殊基金资金卡、批量注资或基金月度市值快照。
- 不把资产划转计为收入、消费或日常收支流水。
- 不根据旧版已折叠的数据猜测具体基金分配。

## 决策

### 使用独立 `assetTransfers` 台账

每条记录保存日期、来源储蓄卡、目标类型、目标卡、金额、是否已由本次操作应用到储蓄余额、是否已由本次操作应用到本金、备注和创建时间。独立台账比复用 `transactions` 更合适，因为后者围绕日常流水派生余额，而统计使用的是 `savingsActuals` 月度余额；混用会造成同一笔钱在两个余额模型中重复生效。

考虑过复用成对 `TRANSFER` 流水，但它无法自然表达单边增加基金本金和“本金已包含”的历史补录，因此不采用。

### 正常划转原子更新当月储蓄余额

正常划转在 `savingsActuals` 中扣减来源卡当月余额；目标为储蓄卡时，同时增加目标卡当月余额。若某卡当月尚无记录，以该月之前最近余额为基数，没有历史余额则以期初余额为基数创建当月记录。来源余额不足时拒绝划转。记录使用 `savingsApplied=1` 标识已经改过余额，撤销时据此反向恢复；“本金已包含”的历史补录记为 0，撤销时禁止重复调整余额。

v17 升级会按日期顺序补算升级前的正常划转，解决已经创建的接收卡记录缺失问题。仅当来源/目标卡类型有效且来源当月余额足够时才应用并标记为 1；无法安全补算的旧记录保留为 0，避免产生负余额或部分迁移。

用户仍可在划转后按实际情况校准月度余额；撤销是在当前当月余额上反向应用原金额。存在已应用划转时，“清除本月数据”必须先要求用户撤销相关划转，避免删掉划转所依赖的余额记录。

### 基金本金用原子事务维护

正常储蓄到基金划转在同一个 Dexie 事务内扣减来源余额、新增台账并增加 `fundPrincipal`；撤销时反向恢复来源余额、删除台账并减回本金。历史补录把 `savingsApplied` 与 `principalApplied` 都记为 0，因此新增和撤销均不改既有余额或本金。直接修改本金会写入 `fundPrincipalLogs`，且不得把本金调到低于仍有效的已应用划转合计。

### 对账按截止月份累计基金投入

`fundInvestment` 为日期月份不晚于统计月份的全部储蓄到基金划转金额，包含“本金已包含”的历史补录。差额拆解为：

```text
差额 = 基金盈亏 + 收入差额 + 利息/其他
     - 消费超支 - 预充暂存 - 基金投入
```

所以：

```text
利息/其他 = 差额 - 基金盈亏 - 收入差额
          + 消费超支 + 预充暂存 + 基金投入
```

储蓄卡之间的划转为总资产零和，不进入该拆解金额。

### 删除卡片时原子清理

删除卡片会清理其作为来源或目标的全部划转以及基金本金校准日志。若删除的是划转来源且目标基金仍保留，先撤销由这些记录实际增加的本金，再删除记录，避免基金本金与统计台账脱节；删除目标基金时随基金一并删除，无需额外回退。

### 备份升级为版本 8

导出增加 `assetTransfers` 和 `fundPrincipalLogs`。导入旧版本时补空数组；导入新版时做卡片存在性、卡类型和金额校验，并与其他表在同一事务中全量替换。

## 风险 / 权衡

- [用户可能期待划转自动改变月度储蓄余额] → 界面明确说明该余额是手工快照，划转用于解释资金路径；避免修改历史数据。
- [本金校准可能破坏之后的可撤销性] → 限制校准值不得低于仍有效、由系统实际应用的划转合计。
- [删除来源卡会改变仍保留基金的本金] → 仅回退 `principalApplied=1` 的记录，并在单一事务内完成；历史补录不会被重复扣减。
- [历史数据无法自动还原每只基金的分配] → 提供“本金已包含”补录，由用户选择目标基金，不做不可靠猜测。

## 迁移计划

1. IndexedDB v16 创建两张新表；v17 为可安全补算的旧正常划转联动余额并写入 `savingsApplied=1`，其余旧记录写入 0。
2. 服务和 UI 上线后，由用户使用历史补录登记已包含在本金中的旧划转。
3. 备份格式提升至 v9，同时保持 v1-v8 导入兼容。
4. 回滚代码时 v15 客户端会忽略新表，但新增划转后的基金本金已写入卡片；因此正式回滚前应先导出 v8 备份。
