## 新增需求

### 需求:记录通用资产划转

系统必须允许用户以任意储蓄卡为来源，将正数金额划转到另一张储蓄卡或一只基金，并保存日期、来源、去向、金额、备注和创建时间；来源与目标禁止相同。

#### 场景:储蓄卡划转到储蓄卡

- **当** 用户从储蓄卡 A 向储蓄卡 B 登记一笔资产划转
- **那么** 系统必须保存双方都可查询的记录，禁止修改 A 或 B 的月度储蓄余额，也禁止把它计为收入或消费

#### 场景:储蓄卡划转到基金

- **当** 用户从储蓄卡向基金登记一笔正常资产划转
- **那么** 系统必须在同一原子事务内保存划转并增加目标基金本金，禁止修改来源卡的月度储蓄余额

#### 场景:拒绝非法目标或金额

- **当** 来源不是储蓄卡、目标类型不匹配、来源与目标相同或金额不为正数
- **那么** 系统必须拒绝提交且不写入任何数据

### 需求:历史补录不重复增加本金

系统必须为储蓄卡到基金的划转提供“本金已包含”模式；该模式必须保存完整资金解释记录，但禁止再次修改基金本金。

#### 场景:补录已包含在本金中的投资

- **当** 用户选择“本金已包含”并补录一笔储蓄卡到基金的历史划转
- **那么** 系统必须保存该记录并标记储蓄余额和基金本金均未由本次操作应用，两者保持不变

### 需求:资产划转可原子撤销

系统必须允许用户撤销资产划转。储蓄卡间划转只删除记录；正常基金划转必须同时减回本金；历史补录只删除解释记录。任何撤销均禁止修改月度储蓄余额，任一步失败时必须整体回滚。

#### 场景:撤销储蓄卡间划转

- **当** 用户撤销一笔储蓄卡间划转
- **那么** 系统必须只删除记录，来源卡与接收卡的月度余额保持不变

#### 场景:撤销正常基金划转

- **当** 用户撤销一笔已实际增加基金本金的划转
- **那么** 系统必须在同一原子事务内删除记录并从目标基金本金减去对应金额，来源卡月度余额保持不变

#### 场景:撤销历史补录

- **当** 用户撤销一笔“本金已包含”的历史补录
- **那么** 系统必须只删除解释记录，禁止改变储蓄余额或基金本金

### 需求:修复划转造成的月度储蓄余额重复扣减

系统必须把月度储蓄余额视为用户填写的真实快照；新增资产划转必须写入 `savingsApplied=0`。对于 v17 已写入 `savingsApplied=1` 的记录，升级或导入旧备份时必须加回来源卡对应月份被重复扣减的金额、保留接收卡现有余额，并把标记归零。

#### 场景:升级 v17 数据

- **当** 系统升级一笔 `savingsApplied=1` 的资产划转
- **那么** 系统必须把金额加回来源卡对应月份、保持目标余额不变并把 `savingsApplied` 改为 0

#### 场景:导入 v9 备份

- **当** 系统导入包含 `savingsApplied=1` 的 v9 备份
- **那么** 系统必须执行与数据库升级相同的来源余额修复，并输出 v10 语义的数据

#### 场景:清除存在划转记录的月份

- **当** 用户清除仍存在资产划转记录的储蓄卡月份
- **那么** 系统必须正常清除该月储蓄数据并保留独立划转记录

### 需求:基金本金校准可审计

系统必须为每次实际改变基金本金的人工校准保存修改前金额、修改后金额和创建时间，并禁止把本金校准到低于仍有效的已应用划转合计。

#### 场景:人工校准基金本金

- **当** 用户把基金本金从一个金额修改为另一个金额
- **那么** 系统必须更新本金并新增一条独立校准审计记录

#### 场景:本金未变化

- **当** 用户提交的基金本金与现值相同
- **那么** 系统禁止生成无变化的校准审计记录

#### 场景:校准破坏可撤销性

- **当** 用户尝试把本金改为低于尚未撤销的已应用基金划转合计
- **那么** 系统必须拒绝该校准并保持本金和审计日志不变

### 需求:资产划转备份可往返

系统必须在备份中导出和导入资产划转及本金校准审计，并继续兼容不包含这些字段的旧版备份。

#### 场景:新版备份往返

- **当** 用户导出后再导入包含资产划转和本金校准的备份
- **那么** 系统必须完整恢复两类记录及其关联关系

#### 场景:导入旧版备份

- **当** 用户导入不包含资产划转和本金校准字段的旧版备份
- **那么** 系统必须以空台账继续导入，禁止因此失败
