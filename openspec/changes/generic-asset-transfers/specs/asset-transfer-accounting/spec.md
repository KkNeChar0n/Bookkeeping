## 新增需求

### 需求:记录通用资产划转
系统必须允许用户以任意储蓄卡为来源，将正数金额划转到另一张储蓄卡或一只基金，并保存日期、来源、去向、金额、备注和创建时间；来源与目标禁止相同。

#### 场景:储蓄卡划转到储蓄卡
- **当** 用户从储蓄卡 A 向储蓄卡 B 登记一笔资产划转
- **那么** 系统必须在同一原子事务内扣减 A 的划转月份余额、增加 B 的划转月份余额并保存可查询记录，且禁止把它计为收入或消费

#### 场景:储蓄卡划转到基金
- **当** 用户从储蓄卡向基金登记一笔正常资产划转
- **那么** 系统必须在同一原子事务内扣减来源卡的划转月份余额、保存划转并增加目标基金本金

#### 场景:当月尚无余额记录
- **当** 正常划转涉及的储蓄卡在划转月份尚无余额记录
- **那么** 系统必须使用该月之前最近余额作为基数创建当月记录；没有历史余额时必须使用卡片期初余额

#### 场景:来源余额不足
- **当** 正常划转金额超过来源卡划转月份可用余额
- **那么** 系统必须拒绝整笔划转且禁止写入部分余额或台账数据

#### 场景:拒绝非法目标或金额
- **当** 来源不是储蓄卡、目标类型不匹配、来源与目标相同或金额不为正数
- **那么** 系统必须拒绝提交且不写入任何数据

### 需求:历史补录不重复增加本金
系统必须为储蓄卡到基金的划转提供“本金已包含”模式；该模式必须保存完整资金解释记录，但禁止再次修改基金本金。

#### 场景:补录已包含在本金中的投资
- **当** 用户选择“本金已包含”并补录一笔储蓄卡到基金的历史划转
- **那么** 系统必须保存该记录并标记储蓄余额和基金本金均未由本次操作应用，两者保持不变

### 需求:资产划转可原子撤销
系统必须允许用户撤销资产划转。系统必须反向恢复由该记录实际调整过的储蓄余额；正常基金划转必须同时减回本金；历史补录只删除解释记录。任一步失败时必须整体回滚。

#### 场景:撤销储蓄卡间划转
- **当** 用户撤销一笔已调整双方余额的储蓄卡间划转
- **那么** 系统必须在同一原子事务内增加来源卡当月余额、减少接收卡当月余额并删除记录

#### 场景:撤销正常基金划转
- **当** 用户撤销一笔已实际增加基金本金的划转
- **那么** 系统必须在同一原子事务内恢复来源卡当月余额、删除记录并从目标基金本金减去对应金额

#### 场景:撤销历史补录
- **当** 用户撤销一笔“本金已包含”的历史补录
- **那么** 系统必须只删除解释记录，禁止改变储蓄余额或基金本金

### 需求:正常划转更新月度储蓄余额
系统必须使用 `savingsApplied` 区分已经调整月度余额的正常划转和只补解释的旧记录/历史补录；禁止对未应用余额的记录执行反向余额调整。

#### 场景:升级前旧记录
- **当** 系统升级一笔没有余额应用标记的正常资产划转，且关联卡片有效、来源当月余额足够
- **那么** 系统必须原子补算来源与接收卡余额并标记为已应用

#### 场景:旧记录无法安全补算
- **当** 升级前记录属于历史补录、关联卡片无效或来源当月余额不足
- **那么** 系统必须把它标记为未应用余额并保留解释记录，禁止产生负余额或部分补算

#### 场景:清除包含已应用划转的月份
- **当** 用户尝试清除仍存在已应用资产划转的储蓄卡月份
- **那么** 系统必须拒绝清除并提示先撤销相关划转

### 需求:基金本金校准可审计
系统必须为每次实际改变基金本金的人工校准保存修改前金额、修改后金额和创建时间，并禁止把本金校准到低于仍有效的已应用划转合计。

#### 场景:人工校准基金本金
- **当** 用户把基金本金从一个金额修改为另一个金额
- **那么** 系统必须更新本金并新增一条独立校准审计记录

#### 场景:本金未变化
- **当** 用户提交的基金本金与现值相同
- **那么** 系统禁止生成无变化的校准审计记录

#### 场景:校准破坏可撤销性
- **当** 用户尝试把本金改为低于尚未撤销的已应用基金划转合计
- **那么** 系统必须拒绝该校准并保持本金和审计日志不变

### 需求:资产划转备份可往返
系统必须在备份中导出和导入资产划转及本金校准审计，并继续兼容不包含这些字段的旧版备份。

#### 场景:新版备份往返
- **当** 用户导出后再导入包含资产划转和本金校准的备份
- **那么** 系统必须完整恢复两类记录及其关联关系

#### 场景:导入旧版备份
- **当** 用户导入不包含资产划转和本金校准字段的旧版备份
- **那么** 系统必须以空台账继续导入，禁止因此失败
