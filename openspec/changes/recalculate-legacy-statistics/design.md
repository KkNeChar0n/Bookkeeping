## 上下文

统计页没有持久化统计结果，而是在查询时聚合 IndexedDB 中的原始记录。旧版删卡只移除了卡片本身或只检查了部分流水，因此已删除卡片的 `transactions`、`budgetDetails`、`savingsEntries`、`consumptionBudgets` 等记录仍可能参与历史统计。上一变更修复了新的删除操作，但已经升级到该版本的用户数据库不会自动重新执行删除逻辑。

## 目标 / 非目标

**目标：**

- 让现有用户升级后自动清除所有引用不存在卡片的遗留记录。
- 实际调账中只要一端失效，就按 `transferGroupId` 删除整组；预算调账中删除直接或通过 `peerCardId` 引用失效卡片的两端记录。
- 保留系统虚拟消费账户及其合法流水，并保留所有仍引用有效卡片的历史数据。
- 对旧备份执行相同清理，避免导入后再次污染统计。
- 清理必须与数据库升级或备份导入处于同一事务，失败时禁止留下半清理状态。

**非目标：**

- 不修改任何金额或推断缺失记录。
- 不生成、缓存或回写统计结果；清理后由现有统计服务实时重算。
- 不尝试推断旧 `budgetLines` 聚合金额中无法识别的调账来源，只移除引用不存在卡片或不存在预算快照的行。

## 决策

### 1. 使用 IndexedDB v13 一次性迁移

新增 v13 升级回调，在同一 Dexie 升级事务中读取卡片 ID 集合并清理孤立数据。版本化迁移只执行一次，适合修正已经存在于用户设备上的历史数据库；新安装没有孤立数据，会直接使用最终 schema。

替代方案是在每次打开统计页时过滤。这会让脏数据永久存在，其他服务或备份仍可能读到错误记录，并重复付出扫描成本。

### 2. 用共享的纯函数生成清理计划

清理规则由纯函数根据各表数组生成待删除 ID：

- `budgetLines`：`cardId` 不存在或 `snapshotId` 不存在。
- `transactions`：`cardId` 不存在、非空 `peerCardId` 不存在，或其 `transferGroupId` 所在组包含上述失效记录。
- `budgetDetails`：`cardId` 不存在或非空 `peerCardId` 不存在。
- `savingsActuals`、`savingsEntries`、`savingsLogs`、`initialBalanceLogs`：`cardId` 不存在。
- `consumptionBudgets`：`savingsCardId` 不存在。
- `fundContributions`：`sourceCardId` 或 `fundCardId` 不存在。
- `fundSnapshots`：`fundCardId` 不存在。

数据库迁移按计划批量删除；备份归一化按相同计划过滤数组。这样两条入口不会产生不同口径，也便于直接单元测试规则。

### 3. 不删除空预算快照

清理孤立 `budgetLines` 后可能留下空快照。空快照本身不引用卡片，也不会贡献金额；保留它可避免误删用户显式创建的历史日期节点。缺少对应快照的预算行则一定无效，可以安全删除。

### 4. 备份导入在落库前过滤

`normalizeBackupData` 完成旧消费卡归一化和虚拟账户补齐后，再使用共享清理计划过滤各数组。这样导入事务不会短暂写入孤立数据，导入返回的流水数量也反映实际保留数量。

## 风险 / 权衡

- [旧数据缺少关系元数据，无法还原某些聚合预算调账的另一端] → 不猜测金额，仅删除确定孤立的行；当前有 `peerCardId` 的预算明细和有 `transferGroupId` 的实际调账可以完整清理。
- [误删系统消费流水] → 在生成计划前保证虚拟消费账户存在于有效卡片集合；迁移测试显式覆盖其保留。
- [数据量较大时升级需要扫描多表] → 每张表只读取一次并使用 `Set` 做线性判断，删除使用 `bulkDelete`。
- [迁移中断] → 依赖 Dexie 版本升级事务整体回滚，数据库不会处于部分清理状态。

## 迁移计划

1. 发布包含 IndexedDB v13 的前端。
2. 用户首次打开新版时自动执行孤立数据清理。
3. 后续所有历史统计查询从清理后的原始记录重新计算，无需用户手动操作。
4. 旧备份在导入归一化阶段执行同一清理。

回滚到 v12 不会恢复已经确认孤立的数据；有效卡片及其合法历史记录不变。
