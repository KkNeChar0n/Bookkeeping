## 需求
### 需求:分类可选
系统必须为收入与支出分别提供可选分类清单（如收入：工资/报销/利息/投资收益/其他；支出：餐饮/房租/交通/购物/医疗/其他），且分类清单必须可扩展。

#### 场景:选择分类
- **当** 用户为一笔流水选择分类
- **那么** 系统必须把该分类随流水一并持久化，供统计使用

### 需求:实际层余额可手改并自动留痕
系统必须允许用户在实际层手动修改某卡的当前余额（用于吸收银行利息等）。手改余额时，系统禁止直接覆盖余额字段，必须自动生成一条"调整"(type=adjust)流水，其金额等于"目标余额 − 当前派生余额"，使余额仍由流水派生且历史可追溯。

#### 场景:手改余额生成调整流水
- **当** 用户把某卡实际余额从 X 改为 Y
- **那么** 系统必须生成一条金额为 (Y − X) 的 adjust 流水，使派生余额变为 Y，并保留该调整记录

#### 场景:调整流水不计入收支统计
- **当** 系统进行收入/支出统计
- **那么** 系统必须排除 type=adjust 的流水，使利息/校正不污染消费或收入统计

### 需求:当日消费直接记入虚拟消费账户
系统必须允许用户在消费工作区选择支出分类并录入金额、日期与备注，提交后直接将该笔支出持久化到唯一虚拟消费账户，禁止要求选择消费卡或实际付款储蓄卡。

#### 场景:记一笔当日消费
- **当** 用户选择支出分类、填写正数金额并提交
- **那么** 系统必须按所选日期持久化消费流水并刷新该日期所属月份的已消费、剩余和超支

#### 场景:消费记账无需选卡
- **当** 用户进入消费工作区
- **那么** 系统必须直接允许记账，禁止显示消费卡或付款储蓄卡选择器

#### 场景:修改消费日期后切换月度口径
- **当** 用户把一笔消费的日期从 2026-07 修改为 2026-08
- **那么** 系统必须从 2026-07 已消费中移除该金额并计入 2026-08，两个自然月分别使用各自额度
